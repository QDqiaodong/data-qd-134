# 原料批次谱系与召回实现说明

模块布局（`src/venue_recall/`，与 `venue_occupancy/`、`venue_energy/` 完全分离、
零互相 import；不修改旧库表，不共用数据库文件）：

| 模块 | 职责 |
| --- | --- |
| `contract.py` | 三个输入文档的严格校验、重放判定的规范载荷 |
| `store.py` | SQLite 表结构、WAL 连接、只读快照连接 |
| `dataset.py` | init / ingest / recall / report 的事务语义与谱系计算 |
| `common.py` | 受限 JSON（≤8MB、拒重复键/NaN）、原子发布 |
| `cli.py` | `venue-recall` 入口与退出码 |

## 持久化结构

| 表 | 主键 / 索引 | 内容 | 增长 |
| --- | --- | --- | --- |
| `meta` | PK(key) | schema 版本 | 常数 |
| `venues` | PK(id) | 冻结场地目录 | ≤100 行 |
| `ops` | PK(op_id) | 全部已接受操作及规范载荷（重放判定依据） | 随历史 |
| `lots` | PK(lot_id) | 每批 kind/创建 op/初始克数/剩余克数/隔离标志；耗尽也保留 | 随批次 |
| `consumption` | PK(op_id,lot_id) WITHOUT ROWID | 每次消耗事件（blend 输入与 serve），关联到产出它的操作 | 随历史 |
| `deliveries` | PK(op_id) | serve 的场地归属；召回可追溯，故永久保留 | 随历史 |
| `composition` | PK(lot_id,root_id) WITHOUT ROWID；索引(root_id) | 每批对原始批次的精确组成，分子/分母为十进制文本 | 见下 |
| `recalls` | PK(root_id) | 永久召回集合 | 随召回 |

三个长期保存的结构各自承担一种精确性职责：

- **谱系边与组成**：`consumption` 保存整数克的消耗↔产出关联（库存账务的事实源，
  恒等式 `remaining = initial − Σ consumption` 同事务成立）；`composition` 保存
  传播后的有理数组成。分子/分母用**十进制文本**而非 SQLite INTEGER：契约验收要求
  分母可超过 64 位（测试用三个 ~10⁹ 素数层的连乘 ~10²⁷ 验证），Python 任意精度
  整数与 `Fraction` 直接序列化，SQL 只做等值查找不做数值比较，因此文本无损。
- **剩余库存**：`lots.remaining_grams` 与消耗行在同一事务里更新，崩溃不会暴露
  “扣了库存却没有消耗记录”或反之的中间态；批次永不删除，因此“耗尽也不能重建”
  只是主键存在性检查。
- **召回状态**：`recalls` 只增；`lots.quarantined` 是由召回集合与组成表导出的
  准入标志，在**同一个 `BEGIN IMMEDIATE` 事务**里随根插入一起更新
  （一条按 `composition(root_id)` 索引驱动的 `UPDATE`）。

## 精确传播：创建时单趟 DP，而非查询时枚举

blend 输出创建时，其组成只从**直接输入**已物化的组成计算一次：

```
ratio(O,R) = Σ_inputs g_i · ratio(P_i,R) / G        (G = 本次总输入克数)
```

- 这是谱系 DAG 上的一趟动态规划：每个输出只对直接前驱做 O(输入数 × 组成宽度)
  的分数加法，与 DAG 的深度和路径总数无关。30 层菱形（祖先路径 ≥ 2³⁰）在测试中
  毫秒完成，组成表仅百余行；按克展开（克数可达 10¹²）或按路径枚举在物理上不可能
  完成，两者都被契约明确禁止。
- 分叉后合流的真实质量在汇合处按上式累加一次：同源分叉再汇合的批次对自身比例为
  1（测试断言送达归因是 70/1 而非 140/1）。
- 消耗不改变组成（部分领用沿用原比例），因此组成行在创建后不可变，召回与报告
  读取的是稳定事实。
- 不变式可独立核对：每批组成比例之和恒为 1；全部召回根的质量守恒——受影响库存
  归因加受影响送达归因恒等于这些根的收货总克数（随机 oracle 测试逐项验证）。

## 原子准入：判定与写入都在数据库事务内

- ingest 与 recall 都是单 `BEGIN IMMEDIATE` 事务：批量校验、库存扣减、组成物化、
  重放登记（ingest）或根插入 + 隔离传播（recall）要么整体提交要么整体回滚。
  SQLite 写锁把两个写者串行化：召回与送达竞争时，后到者在 busy_timeout 内等待，
  看到的是先到者已提交的状态，结果必等价于某一个完整串行顺序（线程与进程两组
  竞速测试各跑多轮，终态逐表比对只落在两种串行结果之一）。
- 隔离标志绝不在事务外读取后再决定写入：ingest 在自己的写事务里读批次行上的
  `quarantined`，recall 在自己的写事务里设置它。重放判定先于一切库存规则，
  因此“已接受、后被召回”的操作重试仍被忽略而不是报错。
- report 在 WAL 只读连接的一个读快照里顺序流出，与并发写者互不阻塞；观察者
  只能看到完整的旧代或新代（快照测试：并发写期间所有观察到的报告都属于已知
  串行状态集合）。报告经临时文件 + `os.replace` 原子替换，失败保留旧文件，
  且只读不写库（重复 report 前后全表快照一致）。

## 备选设计及其代价

被选结构是** eager 物化组成 + 派生隔离标志**。自然的备选是**只存原始边
（consumption/lots），召回与报告时懒遍历 DAG**：

1. **查询成本**：懒方案每次 recall/report 都要从召回根向前遍历全部后代子图，
   并用 `Fraction` 自顶向下重算每个受影响批次的组成（单趟 DP 是多项式，但
   是**每次查询**的多项式）；更糟的是 ingest 的准入判定“该批次是否被隔离”
   将变成每次领用都向祖先遍历到召回集合，否则就得重新引入一个派生标志——
   而标志的维护又回到 eager 方案。物化后，准入是批次行上的一次标志读取，
   recall 是一条索引 `UPDATE`，report 是一次线性连接。
2. **写放大**：eager 的代价是每个 blend 输出写 O(组成宽度) 行 composition
   （懒方案只写整数边）。这是最坏情况下 O(批次数 × 原始批次数) 的行数；本仓用
   局部性测试把代价钉死在可核对界内——ingest 只读本批输入批次的组成行
   （主键 seek，小库/大库行计数完全一致），recall 只触达受影响子图
   （400 个无关批次时仍恰隔离 3 行）。对以召回查询为关键路径的业务，这是
   用可预测的写入量换有界的查询延迟。
3. **恢复一致性**：eager 的组成行、隔离标志与产生它们的事实在同一事务提交，
   崩溃后数据库自洽，重启无需任何重建或重放协议。懒方案本身派生态更少，
   但一旦为性能引入任何缓存（隔离标志、增量组成），就必须额外定义崩溃后的
   失效/重建规则；在“召回状态决定库存准入”的安全语义下，把派生态与事实
   绑进同一事务是最简单的可证正确方案。

另一个被否定的变体是**按根逐条路径存组成**（每根一路径一行）：行数随菱形
深度指数增长，且合流支路会被按祖先可达次数重复计入，直接违反契约的
“不能按祖先可达次数重复计入”。

## 失败与重试

- 批量中任一操作失败 → 整批回滚，全表逐表与批前一致（含注入的提交前故障）；
  重试同一批与无故障结果逐字节一致。
- 重放判定基于解析后规范载荷（键排序、数组保序的 JSON 文本）：同载荷忽略、
  异载荷冲突整批拒绝；重试永不二次扣库存。
- init 在兄弟临时库单事务建库后原子改名；非空目标拒绝覆盖，失败不留半成品。
