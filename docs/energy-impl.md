# 场地电能管道实现说明

模块布局（`src/venue_energy/`，与 `venue_occupancy/` 完全分离、零互相 import）：

| 模块 | 职责 |
| --- | --- |
| `contract.py` | 三个输入的严格校验、CSV 流式逐行解析 |
| `external.py` | 定长记录外部归并排序：有界内存 Spiller、分层 fan-in、流式 RunReader |
| `engine.py` | read_id 去重/冲突、相邻区间解释、月界/费率切片、整数 Wh 分配、月度精确汇总 |
| `common.py` | 严格 JSON（拒重复键/NaN）、原子发布 |
| `cli.py` | `venue-energy audit` 入口与退出码 |

## 数据流

```
readings.csv ──逐行解析/校验──▶ 两个 Spiller（同一记录写两份）
                                   │                 │
                     按 read_id 序的 run      按 (meter,time) 序的 run
                                   │                 │
                     分层归并（fan-in 封顶）   分层归并（fan-in 封顶）
                                   │                 │
              流式相邻比对：重复忽略/冲突拒绝   每表时序扫描：解释→切片→汇总
                                   └──────┬──────────┘
                              MonthlyAggregator → 原子 JSON
```

记录在盘上是 17 字节定长头（`>IIQB`：meter 序号 uint32、epoch uint32、寄存器 uint64、
read_id 长度 uint8）加变长 read_id（≤128 字节）。meter 用 meters.json 中的出现序号
替代字符串，使排序键全部为定长整数/短字节，比较与打包都无动态大对象。

## 为什么这个结构同时满足三个硬约束

### 确定性

- 全序键无并列歧义：read_id 序为 `(read_id, meter_idx, observed_at, register_wh)`，
  meter 序为 `(meter_idx, observed_at, register_wh, read_id)`，任何两条记录都可严格排序，
  `heapq.merge` 与分片内 `sorted` 对同一输入产出唯一顺序，与 CSV 原始行序无关。
- 解释、切片、分配、汇总全部是整数/分数确定性运算，没有哈希遍历顺序依赖
  （最终结果再按 `(venue,year,month)` 显式排序），同输入逐字节可复现。

### 冲突检测

- read_id 冲突只需在 **read_id 全序流**上比较相邻记录：相同 read_id 必然相邻，
  字段全等即重复（跳过），否则立刻抛错，整次运行在写任何输出前终止。
- 同表同时刻冲突同理，在 meter 时序流上相邻出现，寄存器不同即拒绝、相同即去重。
- 两类检测都不需要哈希表容纳全部 read_id，因此检测能力不依赖内存容量。

### 资源上限（500 万行、附加内存 ≤128 MiB、不随行数增长）

- 解析期只保留两个有界排序缓冲（默认各 ≤8 MiB / 5 万条），满即落盘，常驻内存与
  总行数无关；meters、tariffs、月度聚合表都是小而有界的结构（月份数受 2000–2100
  与场地数约束，与读数行数无关）。
- 归并读取器 `RunReader` 以 **1 MiB 定长块**回填并处理跨块记录：即使二级归并面对的
  是几十 MB 的大 run，单路占用仍约 1 MiB，不会把整个 run 读进内存。
- `reduce_runs` 把 run 数量按 fan-in（默认 8）分层收敛，最终归并堆大小 ≤ fan-in，
  堆与打开文件句柄数都不随行数增长。
- 实测（`tests/ve_memory_probe.py`，ru_maxrss）：25 万/100 万/250 万/500 万行的峰值
  RSS 分别约 31/31/32/33 MiB，500 万行仍远低于 128 MiB，且曲线基本水平。

## 备选结构及其代价（为什么不用 SQLite/哈希去重）

一个自然的备选是把读数导入嵌入式表（如 stdlib 的 `sqlite3`），在
`(read_id,...)` 与 `(meter_id,observed_at,...)` 上建索引，用 SQL 完成去重与排序。
它功能上可行，但在本约束下代价更差：

1. **写放大**：每条记录要进主表并维护两棵 B 树索引，等于至少三份有序数据落盘，
   加上 WAL 与页分裂，临时空间和实际写入字节数明显高于本方案的“每序一份紧凑
   定长 run + 分层归并”；本方案每个排序序的总写量约为 1 倍数据量 × 归并层数。
2. **恢复语义的额外复杂度**：SQLite 引入 WAL/journal、checkpoint、崩溃回滚与文件锁
   状态机；本管道是一次性批处理，运行结束唯一要保留的产物是原子替换的 report.json，
   临时 run 只是可丢弃的中间态——崩溃后整个 workdir 直接废弃即可，无需任何恢复协议。
   为一次性中间结果支付事务恢复成本没有收益。
3. **内存可控性与依赖面**：SQLite 的页缓存、统计信息与排序辅助内存由库内部管理，
   难以给出严格的随行数有界证明；定长 run + 显式缓冲的预算则完全由
   `buffer_bytes/buffer_records/fan_in` 三个参数决定，且保持“仅标准库”的最小依赖面
   （不新增任何服务、守护进程或并发写者假设）。

另一个备选是进程内哈希表去重 + 一次全量 `list.sort()`：实现最简单，但哈希表与列表
都随行数线性增长，500 万行下仅 Python 对象头与字符串就会突破 128 MiB，直接违反
附加内存上限，故只适合小规模场景，不满足契约。

## 失败与清理

- 所有输入校验与冲突判定发生在输出文件创建之前；输出走临时文件 + `os.replace`，
  任何异常都保留旧报告，拒绝符号链接输出。
- run 文件统一 `.run` 后缀，`finally` 中按后缀清理；归并生成器在 `finally` 中关闭
  全部 `RunReader`，冲突中途打断合并也不泄漏文件描述符（测试以
  `ResourceWarning` 升级为错误的方式守护）。
